## Overview

The Form widget renders a set of input fields that, when submitted, execute a write query (CREATE, MERGE, INSERT, UPDATE) against your database. Use it to build data entry forms, admin tools, or any workflow that requires writing data from the dashboard.

## Query Format

Write a mutation query with `$param_xxx` placeholders for each form field. The form fields editor (in the widget editor) lets you define the fields, their types, and validation rules.

### Cypher

```cypher
CREATE (n:Person {name: $param_name, email: $param_email, age: toInteger($param_age)})
```

### SQL

```sql
INSERT INTO people (name, email, age)
VALUES ($param_name, $param_email, $param_age)
```

## Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| Submit Button Text | text | Submit | Label for the form submit button |
| Success Message | text | Form submitted successfully | Message shown after a successful submission |
| Reset on Success | boolean | true | Clear all form fields after a successful submission |

## Form Fields

Form fields are configured in the widget editor's **Fields** tab (not in Chart Options). Each field has:

- **Parameter name** -- maps to `$param_xxx` in the query
- **Label** -- display text shown to the user
- **Type** -- text, select, multi-select, cascading select, date, date range, relative date or number range (a text field can also be checked as a number, email or date)
- **Required** -- whether the field must be filled before submission
- **Initial value** -- taken from a matching dashboard parameter when one is set; otherwise the field starts empty (a number range starts at its full min–max)

## Tips

- Anyone who can open the dashboard can submit the form: its owner, users it is shared with, admins, and any signed-in user when the dashboard is public. Their role and **write permission** don't matter, and neither does who owns the form's connection. Each submit runs only the query saved with the form, with the values of its fields, on the connection and database it is saved with. The server enforces this and refuses a submit that sends other query text, so in the editor a form you added or changed waits for Save before it can submit.
- Adding a form, or changing a form's query, connection or database, needs access to that connection: you own it, it is shared with the tenant, or you are an admin. Without that access, saving the change is refused, even when the connection is already on the dashboard. A form left as saved keeps working, and you can still move and resize it.
- Use descriptive parameter names like `$param_email` rather than `$param_1` to keep your query readable.
- Enable Reset on Success for data entry workflows where users submit multiple records in a row.
