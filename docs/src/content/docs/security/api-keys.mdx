API keys let you access NeoBoard's REST API without a browser session. They are useful for scripts, CI/CD pipelines, and integrations.

## Creating an API Key

1. Navigate to **Settings > API Keys** in the sidebar
2. Click **Create API Key**
3. Enter a **name** (e.g., "CI Pipeline") and optional **expiration date**
4. Click **Create**
5. **Copy the key immediately** -- it is shown only once and cannot be retrieved later

The key starts with `nb_` followed by a random string.

## Using an API Key

Include the key in the `Authorization` header:

```bash
curl -H "Authorization: Bearer nb_your_key_here" \
  https://your-neoboard.example.com/api/dashboards
```

**JavaScript / fetch:**

```javascript
const response = await fetch("https://your-neoboard.example.com/api/dashboards", {
  headers: {
    Authorization: "Bearer nb_your_key_here",
  },
});
const data = await response.json();
```

**Python / requests:**

```python
import requests

response = requests.get(
    "https://your-neoboard.example.com/api/dashboards",
    headers={"Authorization": "Bearer nb_your_key_here"},
)
data = response.json()
```

## Available Endpoints

Every authenticated endpoint accepts an API key in place of a session. The only endpoints that don't take one are listed below.

| Endpoint | Reason |
|----------|--------|
| `/api/auth/[...nextauth]` | Session-only (NextAuth sign-in handlers) |
| `/api/auth/bootstrap-status` | Public (no auth required) |
| `/api/auth/sso-providers` | Public (no auth required) |
| `/api/features` | Edition and enabled features; the route does no auth check of its own |
| `/api/health` | Public probe; admin detail (version, migrations, credential and scheduler status) only for an admin session or API key |
| `/api/docs` | Public (documentation page) |
| `/api/openapi`, `/api/openapi.json` | Public (API specification) |

### Common Operations

| Operation | Method | Endpoint |
|-----------|--------|----------|
| List dashboards | `GET` | `/api/dashboards` |
| Get dashboard | `GET` | `/api/dashboards/:id` |
| Create dashboard | `POST` | `/api/dashboards` |
| Export dashboard | `GET` | `/api/dashboards/:id/export` |
| Import dashboard | `POST` | `/api/dashboards/import` |
| Execute query | `POST` | `/api/query` |
| Execute write query | `POST` | `/api/query/write` |
| List connections | `GET` | `/api/connections` |
| Test connection | `POST` | `/api/connections/:id/test` |
| Fetch schema | `GET` | `/api/connections/:id/schema` |
| List users (admin) | `GET` | `/api/users` |
| Create user (admin) | `POST` | `/api/users` |

For the full API specification, visit `/api/docs` or `/api/openapi.json` on your NeoBoard instance.

## Key Management

| Operation | Method | Endpoint |
|-----------|--------|----------|
| List your API keys | `GET` | `/api/keys` |
| Create a new key (requires write permission) | `POST` | `/api/keys` |
| Revoke a key (requires write permission) | `DELETE` | `/api/keys/:id` |

Creating and revoking keys require write permission. Admins always have it and readers never do, so a reader, or a creator with write permission turned off, gets `403 Forbidden`, including when trying to revoke a key they created earlier. Ask an admin to restore write permission or to revoke the key for you.

### Expiration

Keys can have an optional expiration date. Expired keys return `401 Unauthorized`. The `lastUsedAt` field is updated on each use for audit purposes.

## Error Responses

Failed authentication returns HTTP status `401`, in one of two bodies. A request with no `Authorization: Bearer nb_…` header and no session (including a token that lacks the `nb_` prefix) is rejected before it reaches the route, with:

```json
{ "error": "Unauthorized" }
```

A request whose `nb_` key is unknown, expired or revoked reaches the endpoint and gets the standard error envelope:

```json
{ "data": null, "error": { "code": "UNAUTHORIZED", "message": "Unauthorized" }, "meta": null }
```

Ensure your key is:
- Correctly prefixed with `nb_`
- Not expired
- Not revoked
- Included in the `Authorization` header (not query params)

## Security Notes

- API keys are hashed with HMAC-SHA256 before storage. NeoBoard never stores the plain-text key.
- Keys use the current role and write permission of the user who created them, read fresh on every request. They also carry that user's tenant.
- Disabling a user does **not** revoke their API keys. Keys are checked only for their hash and expiry, so a disabled user's keys keep working. Only browser sessions are cut off.
- Admins can't revoke another user's keys one at a time. To end a user's API access immediately, delete the user, which removes all their keys.
- Revoked keys are immediately invalid.
- Use short expiration dates for temporary access.
