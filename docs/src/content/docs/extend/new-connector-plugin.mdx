A connector teaches NeoBoard how to talk to a database: how to connect, how to run a query safely, and (optionally) how to describe the schema. The built-in Neo4j and PostgreSQL connectors are written against the same contract you will use — `@neoboard/connector-sdk` — so they are the reference implementations, not special cases.

This page builds a complete connector for an imaginary database, "MyDB", as an **external package**. Every TypeScript block below names its file on the first line, and the blocks together form one package that compiles against the SDK with the `package.json` and `tsconfig.json` from step 7 — a test in the NeoBoard repo checks that in CI, so what you read here is what the types accept.

## What you build

```txt
neoboard-connector-mydb/
├── package.json
├── tsconfig.json
├── src/
│   ├── index.ts        default export: the ConnectorPlugin object
│   ├── descriptor.ts   ConnectorDescriptor — what the connector is, as pure data
│   ├── auth.ts         AuthenticationModule — URI validation, driver lifecycle
│   ├── connection.ts   ConnectionModule — runQuery, checkConnection, listDatabases
│   ├── schema.ts       SchemaManager (optional) — tables and columns for autocomplete
│   └── driver.ts       your database client
└── __tests__/
    └── conformance.test.ts   the SDK's query-safety harness, against a real database
```

The package imports **only** `@neoboard/connector-sdk`. It never imports `@neoboard/connection`, the app, or a path inside the NeoBoard repo — the SDK is the seam, and everything on the other side of it can change.

## 1. The driver

This guide assumes your client has the shape below. Replace the file with the real driver (`pg`, `mysql2`, `mongodb`, …) and adapt the calls in `connection.ts`; nothing else changes. Two of these methods carry the connector's safety guarantees, so make sure your driver can honour them: `readOnly` must be enforced **by the database** (a read-only transaction or session), and `timeoutMs` must abort the statement **server-side**.

```ts
// src/driver.ts
// The shape this guide assumes of your database client. Replace this file
// with the real driver; the rest of the package stays the same.
export interface QueryOptions {
  /** Refuse writes at the database — never by inspecting the query text. */
  readOnly: boolean;
  /** Abort the statement server-side after this many milliseconds. */
  timeoutMs: number;
}

export interface TableInfo {
  name: string;
  columns: { name: string; type: string; nullable: boolean }[];
}

export interface Driver {
  ping(): Promise<void>;
  /** Streams rows; `params` binds the `$name` placeholders in `text`. */
  query(
    text: string,
    params: Record<string, unknown>,
    options: QueryOptions,
  ): AsyncIterable<Record<string, unknown>>;
  listDatabases(): Promise<string[]>;
  listTables(): Promise<TableInfo[]>;
  close(): Promise<void>;
}

export declare function connect(
  uri: string,
  username: string,
  password: string,
): Driver;
```

## 2. The descriptor

Everything your connector **is** — its name, its query language, and every value it needs in order to connect — is one plain object, the `ConnectorDescriptor`. It is pure data: no functions, no driver import, JSON-serializable. You declare *what* you need; NeoBoard decides how the form that collects it looks, so a field carries no layout, class names or components.

```ts
// src/descriptor.ts
import {
  databaseField,
  passwordField,
  poolSizeField,
  timeoutField,
  uriField,
  usernameField,
  type ConnectorDescriptor,
} from "@neoboard/connector-sdk";

export const descriptor: ConnectorDescriptor = {
  type: "mydb",
  label: "MyDB",
  category: "database",
  queryLanguage: "sql",
  supportsWrite: true,
  supportsGraphData: false,
  fields: [
    uriField({
      placeholder: "mydb://localhost:5555",
      protocols: ["mydb:", "mydb+tls:"],
    }),
    usernameField(),
    passwordField(),
    databaseField({
      placeholder: "app",
      description: "Optional — leave empty for the server default.",
    }),
    poolSizeField("10"),
    // This connection's default query timeout; step 4 reads it back.
    timeoutField("queryTimeout", "Query Timeout", "30000"),
    // Anything the builders do not cover is a plain literal.
    { key: "tls", label: "Require TLS", type: "boolean", group: "advanced" },
  ],
};
```

A field is a plain object. `uriField`, `usernameField`, `passwordField`, `databaseField`, `poolSizeField` and `timeoutField(key, label, placeholder?)` are optional shorthands for the fields most connectors share: each returns the literal under NeoBoard's conventional key (`uri`, `username`, `password`, `database`, `maxPoolSize`; a millisecond timeout of 1000–300000 under your own key), and you can adjust one by spreading it — `{ ...databaseField(), required: true }`. The `uriField(...)` call above is exactly:

```json
{
  "key": "uri",
  "label": "URI",
  "type": "uri",
  "group": "connection",
  "required": true,
  "placeholder": "mydb://localhost:5555",
  "protocols": ["mydb:", "mydb+tls:"]
}
```

Each field's `key` is the key its value is **stored** under on the connection, and the key you read it back from in step 3 — so renaming one later is a data migration. The field types:

| `type`     | Value                     | Extra properties                                                                                                   |
| ---------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `text`     | string                    |                                                                                                                    |
| `password` | string — a secret         | A descriptor may have several; every one is a secret.                                                              |
| `uri`      | string                    | `protocols` (required): the accepted schemes, colon included. Host, port range and "no password in the URI" are checked too. |
| `number`   | integer                   | `min`, `max` (inclusive), `unit` (for example `"ms"` — keep it out of the label).                                   |
| `select`   | one of `options[].value`  | `options` (required): `{ label, value }[]`.                                                                        |
| `boolean`  | `true` / `false`          |                                                                                                                    |

Every field also takes `group` (`"connection"` for what it takes to connect, `"advanced"` for tuning that has a sensible default), and optionally `required`, `placeholder` and `description`. A `placeholder` is only ever shown — apply your defaults in code.

The registry **throws** at startup on a malformed descriptor: a field without `key`, `label` or `type`, an unknown `type` or `group`, a duplicate `key`, a `select` without `options`, a `uri` without `protocols`, an invalid `category`, or an `iconSvg` over 16 KB.

The SDK's `validateConfig(descriptor, config)` checks a config against these declarations — required fields, integer ranges, select membership, the URI rules — and returns `{ config, errors }`: the declared values with unknown keys stripped, and one message per failing field. `toDescriptor(plugin)` is the reverse of step 6: it returns the plain-data half of a plugin, which is what may be sent to a browser.

## 3. The authentication module

Your connector is built from **one config bag**: an object holding the values of your descriptor's fields, keyed by `field.key`. There is no separate auth object and no separate options bag — you read `uri`, `password`, `maxPoolSize` and whatever else you declared from the same place.

`AuthenticationModule` owns the credentials and the driver instance. The protected helper it inherits, `_validateUri`, rejects a malformed URI, a missing host, a bad port, or a scheme outside your list — without ever echoing the URI back, since it may carry credentials. The scheme list comes from the descriptor, so it exists once.

```ts
// src/auth.ts
import {
  AuthenticationModule,
  type ConnectorConfig,
} from "@neoboard/connector-sdk";
import { descriptor } from "./descriptor.js";
import { connect, type Driver } from "./driver.js";

const PROTOCOLS =
  descriptor.fields.find((field) => field.type === "uri")?.protocols ?? [];

const text = (value: unknown): string =>
  typeof value === "string" ? value : "";

export class MyDbAuthenticationModule extends AuthenticationModule {
  private driver: Driver | null = null;
  private readonly uri: string;
  private readonly username: string;
  private readonly password: string;

  constructor(config: ConnectorConfig) {
    super();
    this.uri = text(config.uri);
    this.username = text(config.username);
    this.password = text(config.password);
    this._validateUri(this.uri, PROTOCOLS);
  }

  /** Creates the driver lazily; the same instance serves every query. */
  createDriver(): Driver {
    this.driver ??= connect(this.uri, this.username, this.password);
    return this.driver;
  }

  async verifyAuthentication(): Promise<boolean> {
    await this.createDriver().ping();
    return true;
  }

  /** Part of the base class; NeoBoard never calls it — a changed config builds a new module. */
  async updateAuthConfig(): Promise<void> {
    await this.close();
  }

  async close(): Promise<void> {
    await this.driver?.close();
    this.driver = null;
  }
}
```

Read the bag defensively (`typeof value === "string"`): a driver option is the wrong place to discover a wrong type, and the connections API does not validate a config against your descriptor yet (see step 8). Keys you did not declare may be present — NeoBoard keeps its own settings, such as the row cap, on the same stored config — so read your keys and ignore the rest.

Never log the config or an error that quotes it. The built-ins log only an error's code or name — a driver message can carry the connection string.

## 4. The connection module

`ConnectionModule` is where the [query-safety](/security/query-safety) invariants live. `runQuery` reports through callbacks rather than a return value, and the contract around those callbacks is precise — the comments in the code say what each line is for.

### What a row may hold

NeoBoard is one dashboard over many systems, so nothing downstream asks which connector produced a value: charts and tables key on the value's **form** alone. Your connector turns whatever its driver returns into the forms below before calling `onSuccess`. A row crosses JSON on its way to the browser, so every value must survive `JSON.parse(JSON.stringify(value))` unchanged — no `Date`, no `BigInt` (on which `JSON.stringify` throws), no `undefined`, no driver class instance.

| Kind                | Canonical form                                                                                   | Example                                   |
| ------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------- |
| missing             | `null`, never `undefined` — JSON drops an undefined key and the column vanishes from the row     | `null`                                    |
| boolean, string     | as is                                                                                            | `true`, `"Ada"`                           |
| integer             | `number` inside ±(2^53 − 1), otherwise a decimal **string** — never rounded (`integerToRowValue`) | `42`, `"9007199254740993"`                |
| decimal             | `number` when a double holds it exactly, otherwise a decimal string                              | `12.5`, `"0.12345678901234567890"`        |
| float               | finite `number`                                                                                  | `1.5`                                     |
| date                | `YYYY-MM-DD`                                                                                     | `"2024-06-01"`                            |
| date-time           | ISO-8601 with `Z` or `±HH:MM`. A named zone is dropped and its offset kept                       | `"2024-06-01T14:30:05.123+02:00"`         |
| local date-time     | ISO-8601 with **no** offset. A value that has no zone must not gain one                          | `"2024-06-01T14:30:05"`                   |
| time, local time    | `HH:mm:ss[.f…]`, with `Z` / `±HH:MM` only when the value has an offset                           | `"14:30:05+02:00"`, `"14:30:05"`          |
| duration / interval | ISO-8601 duration from `toIsoDuration`; every non-zero component carries its own sign            | `"P1Y2M3DT4H5M6.5S"`, `"P1M-2DT3S"`       |
| graph value         | `GraphNode`, `GraphRelationship` or `GraphPath`, tagged with `$type`                             | `{ "$type": "node", "labels": […], … }`   |
| list, map           | an array or a plain object of row values                                                         | `[1, "a"]`, `{ "x": 1 }`                  |

Column names are the database's own: never rewrite them. Graph values keep fixed key names — a node is `{ $type: "node", identity, elementId, labels, properties }`, a relationship adds `type` and its four endpoint keys (`start`, `end`, `startNodeElementId`, `endNodeElementId`), which are **absent** rather than `null` when the database returned it without its endpoints; a path is `{ $type: "path", start, end, segments, length }`. The types and the `isGraphNode` / `isGraphRelationship` / `isGraphPath` guards are exported by the SDK. Declare `supportsGraphData: true` only if you emit them.

```ts
// src/rows.ts
import { integerToRowValue, type Row, type RowValue } from "@neoboard/connector-sdk";

/** One value, as the driver returned it, into the form the table above names. */
export function toRowValue(value: unknown): RowValue {
  if (value === null || value === undefined) return null;
  if (typeof value === "bigint") return integerToRowValue(value);
  // NaN and ±Infinity are not JSON: they would arrive as null anyway, so say
  // so here rather than let the serialiser decide.
  if (typeof value === "number") return Number.isFinite(value) ? value : null;
  // An instant. If your database also has a date-time WITHOUT a zone, emit
  // that one from its own components instead: toISOString() would present a
  // wall clock as an instant and move it by the server's offset.
  if (value instanceof Date) {
    return Number.isNaN(value.getTime()) ? null : value.toISOString();
  }
  if (Array.isArray(value)) return value.map(toRowValue);
  // Add a branch here for each class your driver returns — its 64-bit
  // integer, decimal, interval (toIsoDuration), node — BEFORE this one, which
  // would otherwise copy the instance's fields as if it were a map.
  if (typeof value === "object") {
    return Object.fromEntries(
      Object.entries(value).map(([key, item]) => [key, toRowValue(item)]),
    );
  }
  return value as RowValue;
}

export function toRow(raw: Record<string, unknown>): Row {
  return toRowValue(raw) as Row;
}
```

```ts
// src/connection.ts
import {
  ConnectionModule,
  ConnectorError,
  ConnectorErrorType,
  QueryStatus,
  collectUpToLimit,
  drainRetainingUpTo,
  determineQueryStatus,
  resolveQueryTimeout,
  type ConnectionConfig,
  type ConnectorConfig,
  type QueryCallback,
  type QueryParams,
  type Row,
} from "@neoboard/connector-sdk";
import { MyDbAuthenticationModule } from "./auth.js";
import { toRow } from "./rows.js";

export class MyDbConnectionModule extends ConnectionModule {
  authModule: MyDbAuthenticationModule;
  /** The timeout field this connector declared in step 2. */
  private readonly queryTimeout: unknown;

  constructor(config: ConnectorConfig) {
    super();
    this.authModule = new MyDbAuthenticationModule(config);
    this.queryTimeout = config.queryTimeout;
  }

  async runQuery<T>(
    { query, params = {} }: QueryParams,
    callbacks: QueryCallback<T>,
    config: ConnectionConfig,
  ): Promise<void> {
    // Settles a blank query as NO_QUERY + onSuccess([]) and returns true.
    if (this.handleEmptyQuery(query, callbacks)) return;

    // Fail closed: only an explicit "WRITE" gets a writable transaction.
    const readOnly = config.accessMode !== "WRITE";

    let rows: Row[];
    try {
      const stream = this.authModule.createDriver().query(query, params, {
        readOnly,
        // A per-query override if NeoBoard sent one, else this connection's
        // own timeout, else the 30 s default — never "no bound".
        timeoutMs: resolveQueryTimeout(config.timeout, this.queryTimeout),
      });
      // MAX_ROWS+1: pull at most rowLimit + 1 rows and keep rowLimit. A read
      // stops as soon as truncation is known; a write must drain to the end,
      // because rows that are never pulled are never modified.
      const collected = readOnly
        ? await collectUpToLimit(stream, config.rowLimit)
        : await drainRetainingUpTo(stream, config.rowLimit);
      // The ONE pass over the rows: turn what the driver returned into row
      // values (rows.ts, above). Up to 100 000 rows may be kept — do not add
      // a second pass.
      rows = collected.rows.map(toRow);
      const rowCount = collected.truncated ? config.rowLimit + 1 : rows.length;
      callbacks.setStatus?.(determineQueryStatus(rowCount, config.rowLimit));
    } catch (error) {
      // A connector failure is reported, never thrown: onFail fires, the
      // promise resolves, and the UI shows a classified error.
      const wrapped = classify(error);
      callbacks.setStatus?.(
        wrapped.type === ConnectorErrorType.TIMEOUT
          ? QueryStatus.TIMED_OUT
          : QueryStatus.ERROR,
      );
      callbacks.onFail?.(wrapped);
      return;
    }
    // Outside the try on purpose. If the caller's onSuccess throws, that is
    // the caller's bug: it must propagate, not become ERROR + onFail.
    callbacks.onSuccess?.(rows as T);
  }

  async checkConnection(): Promise<boolean> {
    try {
      await this.authModule.verifyAuthentication();
      return true;
    } catch (error) {
      // Throw rather than return false: NeoBoard classifies the message into
      // a hint (credentials, network, URI) for the "Test connection" button.
      throw classify(error);
    }
  }

  async listDatabases(): Promise<string[]> {
    try {
      return await this.authModule.createDriver().listDatabases();
    } catch {
      return []; // unsupported or failed: the database field stays free-text
    }
  }

  /** Optional. NeoBoard calls it when an idle module is evicted or credentials change. */
  async close(): Promise<void> {
    await this.authModule.close();
  }
}

/** Map the driver's errors onto the SDK's types so the UI can act on them. */
function classify(error: unknown): ConnectorError {
  const message = error instanceof Error ? error.message : String(error);
  // Replace these with your driver's error codes.
  let type = ConnectorErrorType.QUERY;
  if (/timeout/i.test(message)) type = ConnectorErrorType.TIMEOUT;
  else if (/read.only/i.test(message))
    type = ConnectorErrorType.READ_ONLY_VIOLATION;
  return new ConnectorError(message, type, error);
}
```

What the pieces of `config` and `callbacks` mean:

| You receive                        | What to do with it                                                                                                                                                                                                                                                                                          |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `query`, `params`                  | Run the query exactly as written — never wrap it, never append a `LIMIT`. `params` is a name → value map, the same for every connector: a dashboard parameter arrives as `$param_xxx` in the text with key `param_xxx` in the map. Bind them through the driver. If your driver only binds positional placeholders, rename the tokens inside `runQuery` and pass the values beside the text — the built-in PostgreSQL connector does that in `connection/src/postgresql/positional-params.ts`. Never interpolate a value into the query string. |
| `config.accessMode`                | `"READ"` for every widget except Form widgets, which send `"WRITE"`. Enforce it at the database; anything that is not exactly `"WRITE"` is read-only.                                                                                                                                                       |
| `config.rowLimit`                  | Keep at most this many rows. Detect truncation by pulling one more (`collectUpToLimit` does this) and report `COMPLETE_TRUNCATED`, which the UI turns into a "showing first N rows" banner.                                                                                                                  |
| `config.timeout`                   | An explicit per-query override in milliseconds — **usually unset**. The default is yours to resolve: `resolveQueryTimeout(config.timeout, yourConfiguredTimeout)` returns the override, else the timeout field you declared, else 30 s, and never lets zero or junk mean "unbounded". Enforce the result at the driver or server (statement timeout, transaction timeout, `maxTimeMS` — whatever your database has) and report `TIMED_OUT`. |
| `config.database`                  | The database for this query, or `undefined` for the server default. It is the `database` of your config bag unless a widget overrides it. Applying it is your job — NeoBoard no longer rewrites the URI.                                                                                                    |
| `callbacks.onSuccess(rows)`        | An array of plain row objects whose values follow [What a row may hold](#what-a-row-may-hold) — it is serialised to JSON as-is and handed to the chart transforms, which never ask which connector a value came from. Exactly one of `onSuccess` / `onFail` fires per call.                                   |
| `callbacks.onFail(error)`          | A `ConnectorError` whose `type` says what went wrong. `wrapError` in the SDK only knows the two built-in drivers, so construct the error yourself.                                                                                                                                                           |
| `callbacks.setStatus(status)`      | `RUNNING` is set for you by `handleEmptyQuery`; you set `COMPLETE`, `COMPLETE_TRUNCATED`, `NO_DATA` (`determineQueryStatus` picks), `TIMED_OUT` or `ERROR`.                                                                                                                                                 |

## 5. The schema manager (optional)

If your database can describe its tables, implement `SchemaManager` and the query editor gets autocomplete and a schema panel for connections of your type. Omit it otherwise — the registry resolves a missing manager to `undefined` and the editor works without it. `type` is a free string, so use your connector's `type`.

```ts
// src/schema.ts
import type {
  ConnectorConfig,
  DatabaseSchema,
  SchemaManager,
} from "@neoboard/connector-sdk";
import { MyDbConnectionModule } from "./connection.js";

export class MyDbSchemaManager implements SchemaManager {
  /** Takes the same config bag as `createModule`. */
  async fetchSchema(config: ConnectorConfig): Promise<DatabaseSchema> {
    const module = new MyDbConnectionModule(config);
    try {
      const tables = await module.authModule.createDriver().listTables();
      return { type: "mydb", tables };
    } finally {
      await module.close();
    }
  }
}
```

## 6. The plugin object

The package's default export is the `ConnectorPlugin`: the descriptor plus the factories that need the driver. `createModule` is the only place a driver gets instantiated, and it is the only method NeoBoard calls with credentials.

```ts
// src/index.ts
import type { ConnectorPlugin } from "@neoboard/connector-sdk";
import { MyDbConnectionModule } from "./connection.js";
import { descriptor } from "./descriptor.js";
import { MyDbSchemaManager } from "./schema.js";

const plugin: ConnectorPlugin = {
  ...descriptor,
  createModule(config) {
    return new MyDbConnectionModule(config);
  },
  createSchemaManager() {
    return new MyDbSchemaManager();
  },
};

export default plugin;
```

Keeping the descriptor in its own file, with type-only imports, is what lets it be bundled for a browser: importing `index.ts` pulls in your driver, importing `descriptor.ts` pulls in nothing.

What NeoBoard does with each field today — read this before relying on one:

| Field                                                | Required | Used by                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type`                                               | yes      | Stored on each connection; the API accepts any registered type; it selects your module for queries, connection tests, database listing and schema fetches. Chart types and widget templates do not accept it yet — see step 8.                                                                                                                     |
| `label`, `category`                                  | yes      | Validated by the registry and by `neoboard plugin add` (`category` must be `database`, `graph`, `api` or `file`). The "Add Connection" picker and the widget library's connector filter show `label`; `category` picks the picker's sub-label and the fallback icon.                       |
| `createModule(config)`                               | yes      | Called once per distinct config — the cache key is a hash of the whole bag, so changing any value builds a new module. The instance is reused for every query and `close()`d after 30 minutes idle or when the connection changes.                                                          |
| `createSchemaManager()`                              | no       | The connection's schema endpoint and the editor's autocomplete prefetch.                                                                                                                                                                                                                   |
| `queryLanguage`                                      | no       | The query editor's language for a connection of your type, and the highlighting of its saved templates. `cypher` and `sql` are the grammars that ship; any other value, or none, gives a plain-text editor.                                                                                |
| `fields`                                             | yes      | Validated by the registry, which throws on a malformed one (step 2). Their keys are the keys of the config bag. The "Add Connection" dialog lists your connector and renders its `connection` group; the advanced options, the edit dialog and validation are still the built-in connectors' own, so create a connection of your type through the API — see below. Use `[]` for a connector with no config.|
| `iconSvg`                                            | no       | Inline SVG markup, at most 16 KB, shown in the type picker and on connection cards. Make it a standalone document (`xmlns="http://www.w3.org/2000/svg"`, its own colours): it is rendered as an image, never as markup, so scripts, event handlers and external references in it do nothing. Without one you get a generic icon for your `category`.|
| `supportsWrite`, `supportsGraphData`                 | no       | Declarative; nothing reads them yet.                                                                                                                                                                                                                                                       |

## 7. Package it

```json title="package.json"
{
  "name": "neoboard-connector-mydb",
  "version": "0.1.0",
  "type": "module",
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "files": ["dist"],
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "test": "vitest run"
  },
  "peerDependencies": {
    "@neoboard/connector-sdk": "0.1.0"
  },
  "devDependencies": {
    "@types/node": "^26.2.0",
    "typescript": "~5.9.3",
    "vitest": "^4.1.11"
  }
}
```

Name it `neoboard-connector-<name>` so it is findable, and depend on the SDK as a **peer** dependency so your connector and NeoBoard share one copy of the base classes — `instanceof` and the registry's checks depend on that.

```json title="tsconfig.json"
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "dist",
    "declaration": true,
    "strict": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

The package is an ES module (`"type": "module"`) compiled with `NodeNext` resolution, which is why every relative import in the blocks above ends in `.js`: Node's module loader does not add extensions, and TypeScript resolves `./auth.js` to `src/auth.ts`. `npm run build` writes `dist/`, where `main` points.

The SDK is versioned with NeoBoard and lives at `connector-sdk/` in the repository. It is not on the npm registry yet, so until it is, install it from a checkout: `npm install --save-dev ../neoboard/connector-sdk` from your package's directory adds a `file:` dev dependency and builds it on install. Keep it out of `dependencies` — NeoBoard supplies the peer, and a `file:` path there would ship inside your package.

## 8. Load it into NeoBoard

External connectors are compiled into the server, not discovered at runtime. The manifest at the repository root lists them, and a generator turns the manifest into a static import list that the registry reads at startup. From the root of a NeoBoard checkout:

1. Install your package under its package name. Once it is on the npm registry that is `npm install neoboard-connector-mydb`. Until then, pack it and install the tarball, which copies it into `node_modules` the way a registry install does:

   ```bash
   # in neoboard-connector-mydb/
   npm run build && npm pack
   # in the NeoBoard checkout
   npm install ../neoboard-connector-mydb/neoboard-connector-mydb-0.1.0.tgz
   ```

2. Add it to `neoboard-connectors.json`:

   ```json
   {
     "connectors": [{ "package": "neoboard-connector-mydb" }]
   }
   ```

3. Run `npm run dev` or `npm run build`. Both run `scripts/generate-connector-imports.mjs` first, which checks that every listed package is installed and writes `connection/src/external-connectors.generated.ts`. The connector is part of that build.

Each entry may also carry `"export": "<name>"` when the plugin is not the package's default export, and `"overrides": true` to replace a connector with the same `type` — without it, a duplicate `type` throws at startup so a conflict cannot pass silently.

A Docker image built from the checkout installs dependencies with `npm ci` from `package.json` and `package-lock.json` alone, so it can include your connector only once the package is installed from a registry.

`neoboard plugin add` does not work for a connector built on the SDK yet. It is meant to replace steps 1 and 2: it installs a package, imports it to validate the export (`type`, `label`, `category`, `createModule`), adds the manifest entry and runs the generator. But it imports the package in plain Node, and Node cannot load the SDK's build — the SDK compiles to ES modules whose relative imports carry no file extension, which only a bundler resolves — so the import throws and the CLI uninstalls the package again. It also installs and imports the name you give it, so it needs a published package. Use the three steps above until both change (#1697).

To create a connection of your type, call the API (the dialog offers only the built-in types today):

```bash
curl -X POST http://localhost:3000/api/connections \
  -H "Authorization: Bearer nb_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "MyDB",
    "type": "mydb",
    "config": {
      "uri": "mydb://db.internal:5555",
      "username": "app",
      "password": "…",
      "database": "app"
    }
  }'
```

The connections API does not validate `config` against your descriptor yet: it applies one fixed schema to every type. `uri`, `username` and `password` are required, `database` and the built-in connectors' options (`connectionTimeout`, `queryTimeout`, `maxPoolSize`, `connectionAcquisitionTimeout`, `idleTimeout`, `statementTimeout`, `sslRejectUnauthorized`) are accepted, and **any other key is dropped before the config is stored**. Until that changes, name your fields from that list.

The key needs a creator or admin role ([API keys](/security/api-keys)). "Test connection" then calls your `checkConnection`, the database picker calls `listDatabases`, and the editor fetches your schema. Charting it is limited today, because two places still know only the built-in types. The widget editor treats no chart type as compatible with your type (`getCompatibleChartTypes` returns nothing for a type outside `CONNECTOR_TYPES`): choosing the connection resets the widget to a table, and the chart picker offers only the widget's current type. And the widget-templates API rejects a template whose `connectorType` is not a built-in one, so such a widget cannot be saved as a template.

## 9. Prove query safety

The SDK ships a conformance harness: five cases that check what the database actually does, not what the code says. Run them in your own test runner against a real instance of your database — a mock cannot satisfy them.

```ts
// __tests__/conformance.test.ts
import { afterAll, beforeAll, describe, test } from "vitest";
import {
  DEFAULT_CONNECTION_CONFIG,
  buildConformanceCases,
  type ConformanceSetup,
} from "@neoboard/connector-sdk";
import { MyDbConnectionModule } from "../src/connection.js";

describe("MyDB query-safety conformance", () => {
  let connection: MyDbConnectionModule;

  beforeAll(async () => {
    // Start a real database first (Testcontainers, docker compose, a CI
    // service) and point the module at it.
    connection = new MyDbConnectionModule({
      uri: process.env.MYDB_URI ?? "mydb://localhost:5555/app",
      username: "app",
      password: process.env.MYDB_PASSWORD ?? "",
    });
  });

  afterAll(async () => {
    await connection?.close();
  });

  const setup: ConformanceSetup = {
    baseConfig: DEFAULT_CONNECTION_CONFIG,
    queries: {
      // Mutates data — must be refused under READ access mode.
      write: { query: "CREATE TABLE conformance_tmp (x int)" },
      // Returns as many rows as $param_rows says, so the cap is observable.
      // The harness binds it by name — { param_rows: n } — as NeoBoard does.
      manyRows: "SELECT * FROM series(1, $param_rows)",
      // Runs longer than the 250 ms timeout the harness configures.
      slow: { query: "SELECT sleep(5)" },
    },
  };

  for (const c of buildConformanceCases(() => connection, setup)) {
    test(c.name, c.run);
  }
});
```

The cases, and what each one fails on:

| Case                                                       | Fails when                                                                                                                                 |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| rejects a write query under READ access mode               | the write succeeds — no `onFail`, no `ERROR` status                                                                                        |
| caps results at rowLimit and flags truncation (MAX_ROWS+1) | `onSuccess` gets anything other than an array of exactly `rowLimit` rows — which is also what dropping the named parameter looks like — or `COMPLETE_TRUNCATED` is never set |
| honors the driver-level timeout                            | a slow query neither fails nor reports `TIMED_OUT` within the configured timeout                                                           |
| bounds a slow query when timeout is unset                  | `config.timeout` is unset — what NeoBoard sends for an ordinary query — and the slow query runs past the default timeout                 |
| does not report a throwing onSuccess as a query failure    | a throwing `onSuccess` reaches `onFail` or sets `ERROR`, or `runQuery` rejects with anything but the caller's own error                    |

The built-in connectors run the same cases against Neo4j and PostgreSQL containers in `connection/__tests__/conformance/` — copy their queries if your database speaks Cypher or SQL.

## 10. Prove result shapes

Query safety is how a query runs; this is what its rows hold. `buildShapeConformanceCases` checks your row conversion against [What a row may hold](#what-a-row-may-hold), and unlike step 9 it needs **no database**: you hand it a function that converts one raw value, plus raw values you build yourself — exactly what your driver would return — each with the row value it must become.

```ts
// __tests__/shapes.test.ts
import { describe, expect, test } from "vitest";
import {
  buildShapeConformanceCases,
  type ShapeFixtures,
} from "@neoboard/connector-sdk";
import { toRowValue } from "../src/rows.js";

const fixtures: ShapeFixtures = {
  safeInteger: { raw: 42, expected: 42 },
  // 2^53 + 1: a double rounds it to …992, so it must come out as a string.
  unsafeInteger: { raw: 9007199254740993n, expected: "9007199254740993" },
  float: { raw: 1.5, expected: 1.5 },
  boolean: { raw: true, expected: true },
  // Every way your driver says "no value".
  nullish: [
    { raw: null, expected: null },
    { raw: undefined, expected: null },
  ],
  // Driver values at depth: the conversion has to recurse.
  nested: {
    raw: [{ ids: [1, 7n], seen: new Date("2024-06-01T12:30:05.123Z") }],
    expected: [{ ids: [1, 7], seen: "2024-06-01T12:30:05.123Z" }],
  },
  dateTime: {
    raw: new Date("2024-06-01T12:30:05.123Z"),
    expected: "2024-06-01T12:30:05.123Z",
  },
};

describe("MyDB result-shape conformance", () => {
  const cases = buildShapeConformanceCases(toRowValue, fixtures, {
    // The descriptor's own value. When true, the four graph fixtures
    // (node, relationship, relationshipWithoutEndpoints, path) are mandatory.
    supportsGraphData: false,
  });

  // Pin the list: a fixture that goes missing would otherwise pass in silence.
  test("covers every kind this database has", () => {
    expect(cases.map((c) => c.name)).toEqual([
      "safeInteger",
      "unsafeInteger",
      "float",
      "boolean",
      "nullish",
      "nested",
      "dateTime",
    ]);
  });

  for (const c of cases) {
    test(c.name, c.run);
  }
});
```

The first six kinds are mandatory. Add a fixture for every other type your database has — `decimal`, `date`, `dateTime`, `localDateTime`, `time`, `localTime`, `duration` — and leave out the ones it lacks: a kind with no fixture generates no case. A fixture may be a list, so give `duration` a negative and a mixed-sign example. When parsing depends on the column type, make the raw value carry it (`{ value, oid }`) and unpack it in the function you pass.

Each fixture is checked three ways, and a case throws on the first violation:

| Check          | Fails when                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JSON safety    | anywhere in the value, at any depth, there is a `Date`, a `BigInt`, a function, `undefined`, a non-finite number, a `{low, high}` driver integer or a class instance — or the value does not survive `JSON.parse(JSON.stringify(value))` |
| Canonical form | the value is not the form of its kind: a graph value without its `$type` tag, a date-time that is not ISO-8601, a rounded number where a decimal string is required                          |
| Expected value | the form is right and the value is wrong — the right shape holding the previous day                                                                                                         |

The built-in connectors run the same cases over their record parsers in `connection/__tests__/conformance/neo4j-shapes.test.ts` and `pg-shapes.test.ts`, with values built from their drivers' own classes.

## Contributing a built-in instead

The built-ins live under `connection/src/<name>/` and are registered in `connection/src/connector-registry.ts`, right before the external list. A core connector is the same code as above minus the package boilerplate, plus integration tests under `connection/__tests__/` against a Testcontainers database — see [Testing](/extend/testing). Open an issue first: a built-in adds a driver to every NeoBoard image.
