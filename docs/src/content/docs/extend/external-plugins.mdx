External plugins let you add chart types and database connectors to NeoBoard **without modifying the core code**. You can package one as an npm package, but it is compiled into a NeoBoard build from source, not installed into a running instance. Install the package in a NeoBoard checkout, list it in `neoboard-connectors.json` (connectors) or `neoboard-plugins.json` (charts), and run `npm run dev` or `npm run build` from the repository root. That regenerates the static import list. A running instance or a prebuilt image cannot load a plugin.

The [chart plugin guide](/extend/new-chart-plugin) covers adding a built-in chart type, which needs a PR to the NeoBoard repository. The [connector guide](/extend/new-connector-plugin) builds a connector as an external package.

## When to Create an External Plugin

- You want to support a database that NeoBoard doesn't ship with
- You want to add a custom chart type for your organization
- You want to distribute a plugin via npm without forking NeoBoard

## Trust Boundary

A connector is not sandboxed. It is compiled into the NeoBoard server and runs in the server's process with the server's privileges: its network access, its environment (`ENCRYPTION_KEY` included) and the decrypted config of every connection of its type. It also owns its read-only enforcement. NeoBoard asks for a read, but only the connector can make the database refuse a write, so a connector that ignores the access mode lets a dashboard widget write.

NeoBoard backstops two of a connector's promises, and only on what comes back, never on the query. A result longer than the row cap is cut to the cap and marked truncated. A query the connector has not answered by the longest millisecond timeout its connection holds (never less than 30 seconds), plus 10 seconds, fails with a timeout, and its place in the connection's query queue is freed.

Install only connectors you trust, and run the SDK's [conformance harness](/extend/new-connector-plugin#9-prove-query-safety) against a real database before you build one in.

## Plugin Architecture

A connector plugin is a `ConnectorDescriptor` — pure data saying what the connector is and which config it needs — plus the factories that need a database driver:

```ts
interface ConnectorDescriptor {
  type: string;             // Unique identifier (e.g., "mongodb")
  label: string;            // Display name
  category: string;         // "database", "graph", "api", "file"
  queryLanguage?: string;   // CodeMirror syntax (e.g., "json", "sql")
  fields: ConnectorField[]; // Every value the connector reads from its config
}

type ConnectorPlugin = ConnectorDescriptor & {
  createModule(config: Record<string, unknown>): ConnectionModule;
  createSchemaManager?(): SchemaManager;
};
```

`createModule` takes one config bag: the values of `fields`, keyed by each field's `key`. The connector builds its own driver auth from it, so nothing — not even a username — is mandatory for every connector.

A chart plugin is created with `defineChartPlugin()`:

```ts
defineChartPlugin({
  type: "heatmap",
  label: "Heatmap",
  component: HeatmapComponent,
  transform: transformToHeatmapData,
  settingsSchema: heatmapSettingsSchema,
  capabilities: { ... },
});
```
