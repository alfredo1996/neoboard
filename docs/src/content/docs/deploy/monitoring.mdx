## Health check endpoint

NeoBoard exposes a health check at `GET /api/health` that reports:

- Overall status, from environment configuration and the database
- Database connectivity and latency

```bash
curl -s http://localhost:3000/api/health | jq
```

```json
{
  "data": {
    "status": "ok",
    "db": {
      "status": "ok",
      "latencyMs": 4
    }
  }
}
```

### Status values

| Status | HTTP Code | Meaning |
|--------|-----------|---------|
| `ok` | 200 | All systems operational |
| `degraded` | 200 | Running, with a configuration warning. Today the only warning is an incomplete OIDC group: some but not all of `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` are set, so SSO will not work. Database latency never changes the status. To catch a slow database, alert on `db.latencyMs` directly. |
| `error` | 503 | Missing required configuration or DB unreachable |

The public payload above is the up/down answer only. Which variables are set, and which fail validation (`config`, `errors`, `warnings`), is shown to an admin only, and never as a value: `config` reports each variable as `set`/`unset`.

### Extended payload for admin sessions

When called with an authenticated **admin** session, `/api/health` returns extra operational intel (kept off the unauthenticated surface):

- `errors`, `warnings` — the configuration problems behind a `degraded` or `error` status
- `config` — each known variable as `set` or `unset`
- `version` — app + Node version
- `migrations` — `applied` / `expected` / `upToDate` and `lastAppliedAt` (detects migration drift after an upgrade)
- `schedulers` — per-connector query-scheduler stats (queue depth, in-flight, shed counts) for spotting backpressure

An anonymous or non-admin caller always gets the public shape, so health probes remain unauthenticated.

### Using with Docker

The NeoBoard image ships its own health check, so the production compose files (`docker-compose.prod.yml`, `docker-compose.prod-full.yml`) need none. From the Dockerfile:

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=30s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://127.0.0.1:3000/api/health || exit 1
```

To override it, add a `healthcheck:` block to the `neoboard` service.

### Using with Kubernetes

```yaml
livenessProbe:
  httpGet:
    path: /api/health
    port: 3000
  initialDelaySeconds: 30
  periodSeconds: 30
  timeoutSeconds: 10

readinessProbe:
  httpGet:
    path: /api/health
    port: 3000
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 5
```

A complete Deployment and Service using these probes is on [Run from a build](/deploy/run-from-a-build#option-2-kubernetes-with-the-published-image).

## Key metrics to monitor

### Application health

| Metric | How to check | Alert threshold |
|--------|-------------|-----------------|
| Health endpoint | `GET /api/health` | HTTP status != 200 |
| DB latency | `health.db.latencyMs` | > 500ms |
| Response time | Load balancer / reverse proxy logs (every route); for the query routes, [Metrics](/deploy/metrics): `neoboard_http_request_duration_seconds` | p95 > 2s |
| Error rate | Application or proxy logs, 5xx on every route; for the query routes, [Metrics](/deploy/metrics): `neoboard_http_requests_total` by `status` | > 1% of requests |

### Infrastructure

| Metric | How to check | Alert threshold |
|--------|-------------|-----------------|
| CPU usage | Docker stats / cAdvisor | > 80% sustained |
| Memory usage | Docker stats / cAdvisor | > 80% of limit |
| Disk usage | `df -h` on data volumes | > 85% |
| PostgreSQL connections | `SELECT count(*) FROM pg_stat_activity` | > 80% of `max_connections` |
| PostgreSQL replication lag | `pg_stat_replication` | > 10s (if using replicas) |

### Database health queries

```sql
-- Active connections
SELECT count(*) AS active_connections FROM pg_stat_activity
WHERE datname = 'neoboard';

-- Database size
SELECT pg_size_pretty(pg_database_size('neoboard')) AS db_size;

-- Largest tables
SELECT relname AS table, pg_size_pretty(pg_total_relation_size(relid)) AS size
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;

-- Slow queries (requires pg_stat_statements extension)
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;
```

## Uptime monitoring

For external uptime monitoring, point your preferred tool at the health endpoint:

- **UptimeRobot** (free): Monitor `GET /api/health`, alert on non-200
- **Better Uptime**: Same endpoint, add status page
- **Pingdom**: HTTP check on `/api/health`

## Log monitoring

NeoBoard writes its application logs to stdout as JSON by default, so no setup is needed (`LOG_FORMAT` defaults to `json`; `LOG_FORMAT=pretty` is for local development only). Key log fields:

| Field | Description | Where it appears |
|-------|-------------|------------------|
| `level` | Log severity as a Pino number: `30` info, `40` warn, `50` error | all logs |
| `msg` / `event` | Human-readable message / structured event name | all logs |
| `requestId` | Correlation ID for tracing a request end-to-end | **every** `api_error` log, plus the query routes' `request_start`/`request_end` and query audit logs |
| `durationMs` | Request/query duration in milliseconds | query request logs (`request_end`) and query audit logs |
| `userId` | Authenticated user | where a session is resolved (e.g. audit logs) |

:::note
`requestId` is stamped on every request by the proxy layer and is included in **all** error logs, so any failed request can be traced across its logs by that id. Full request-lifecycle timing (`durationMs`, `status`) is currently emitted for the query-execution routes (`/api/query`, `/api/query/write`) and audit logs — not yet every CRUD route — so the duration filter below applies to that traffic.
:::

### Filtering logs

```bash
# The prod compose files require their secrets, so pass the env file on every call
C="docker compose --env-file docker/.env.production.local -f docker/docker-compose.prod-full.yml"

# View errors only (Pino levels: 50 = error, 40 = warn, 30 = info)
$C logs --no-log-prefix neoboard 2>&1 | jq -R 'fromjson? | select(.level >= 50)'

# Trace one request across all its logs by correlation id
$C logs --no-log-prefix neoboard 2>&1 | jq -R 'fromjson? | select(.requestId == "REQUEST-ID")'

# View slow query requests (> 1s) — query routes / audit logs carry durationMs
$C logs --no-log-prefix neoboard 2>&1 | jq -R 'fromjson? | select(.durationMs > 1000)'

# View a specific user's activity (audit logs)
$C logs --no-log-prefix neoboard 2>&1 | jq -R 'fromjson? | select(.userId == "user-uuid")'
```

`fromjson?` skips the non-JSON startup and stderr lines. For `docker-compose.prod.yml`, change the `-f` path and supply its required variables (`DATABASE_URL`, `ENCRYPTION_KEY`, `NEXTAUTH_SECRET`, `API_KEY_HMAC_SECRET`) the same way, with `--env-file` or from the shell environment; without them compose refuses to run. For the CLI stack, the container is `neoboard-app` (`docker logs neoboard-app`).

### Log aggregation

The repo ships a Fluent Bit kit that puts the app's logs into OpenSearch, searchable in OpenSearch Dashboards. The app already writes one JSON object per line to stdout, so nothing in the app changes. Each line arrives with its own time as the event time, `severity` (`info`, `warn`, `error`, ...) next to pino's numeric `level`, and every field (`requestId`, `durationMs`, `schedulerWaitMs`, ...) searchable.

#### Docker

Layer the add-on on a production compose file:

```bash
docker compose --env-file docker/.env.production.local \
  -f docker/docker-compose.prod-full.yml -f docker/docker-compose.logging.yml up -d
```

It works the same with `docker-compose.prod.yml`. Open Dashboards at `http://localhost:5601` and create the index pattern `neoboard-*`. Then search `event:query_executed` to see every query with its timings.

- The app logs through Docker's `fluentd` driver to Fluent Bit; `docker logs` keeps working.
- One index a day (`neoboard-YYYY.MM.DD`), deleted after 14 days by the policy in `deploy/opensearch/ism-neoboard-14d.json`.
- If OpenSearch is down, Fluent Bit keeps the logs in a disk buffer (the `fluentbitbuffer` volume) and retries until it is back. The buffer is capped at 1 GB (`storage.total_limit_size` in the output): that cap is the only limit, and past it the oldest buffered logs are dropped, so disk use stays bounded. Raise it for a longer outage.
- OpenSearch runs single-node with a 512 MB heap and **without its security plugin**, and every port is bound to `127.0.0.1`. That suits a laptop or a trusted single server; put authentication in front before exposing any of it.

#### Kubernetes

A DaemonSet reads the app pods' stdout from each node. The output points at `opensearch-cluster-master`, the service of the official OpenSearch chart, which runs its security plugin by default: HTTPS on 9200 with basic auth. The values read the user and password from the environment, the password from a Secret you create first, and verify the OpenSearch certificate against the CA in a second Secret (`tls.verify On`, `tls.ca_file`), so nothing but your OpenSearch receives the password and the logs. Point `Host` at your own OpenSearch service if it differs.

If OpenSearch is down, each node keeps the logs in a buffer directory on its disk (`/var/lib/fluent-bit-buffer`, a `hostPath` mounted through the chart's volume values) and retries until it is back. The buffer is capped at 1 GB per node (`storage.total_limit_size`): that cap is the only limit, and past it the oldest buffered logs are dropped.

Install the 14-day retention policy before any log is shipped, so every `neoboard-*` index picks it up as it is created (the policy's `ism_template` attaches it). Through a port-forward, with the CA saved as `ca.crt`:

```bash
kubectl -n logging port-forward svc/opensearch-cluster-master 9200:9200 &
OS="curl -sS --cacert ca.crt -u admin:<the OpenSearch admin password> https://localhost:9200/_plugins/_ism"
$OS/policies/neoboard-14d -X PUT -H 'Content-Type: application/json' \
  --data-binary @deploy/opensearch/ism-neoboard-14d.json
# attach it to any index that already exists
$OS/add/neoboard-* -X POST -H 'Content-Type: application/json' -d '{"policy_id":"neoboard-14d"}'
```

Then install the chart with the shipped values:

```bash
kubectl -n logging create secret generic opensearch-credentials \
  --from-literal=password='<the OpenSearch admin password>'
kubectl -n logging create secret generic opensearch-ca \
  --from-file=ca.crt=ca.crt
helm repo add fluent https://fluent.github.io/helm-charts
helm upgrade --install fluent-bit fluent/fluent-bit --version 0.58.3 \
  -n logging --create-namespace -f deploy/kubernetes/fluent-bit-values.yaml
```

For the official OpenSearch chart's self-signed demo certificate only, replace `tls.verify On` and `tls.ca_file` in the values with `tls.verify Off`. The password is then sent to whatever answers on that address, so keep that to a test cluster.

The `tail` input reads `/var/log/containers/*neoboard*.log`. That also matches a namespace named `neoboard`, and the product rename (#1974) changes the pod names: edit `Path` in the values to match yours.

No sidecar is needed while the app logs to stdout (the default). If you set `LOG_OUTPUT=file`, the logs go to `LOG_FILE_PATH` inside the pod: mount that directory on a volume shared with a Fluent Bit sidecar whose `tail` input reads the file and uses the same filters and output.

#### Another destination

Only OpenSearch is tested. To send the logs elsewhere, replace the `[OUTPUT]` block of `deploy/fluent-bit/fluent-bit.conf` (or `config.outputs` in the values) with the matching Fluent Bit output: `loki` for Grafana Loki, `cloudwatch_logs`, `datadog`. The parser and the severity filter stay as they are. For Elasticsearch and Kibana:

```ini
[OUTPUT]
    Name                es
    Match               *
    Host                elasticsearch.example.com
    Port                9200
    tls                 On
    HTTP_User           ${ELASTIC_USER}
    HTTP_Passwd         ${ELASTIC_PASSWORD}
    Logstash_Format     On
    Logstash_Prefix     neoboard
    Suppress_Type_Name  On
```

#### Checks

CI validates the Fluent Bit config (`--dry-run`, a few seconds of startup in the pinned image, and the Lua filter on sample lines), the compose add-on and the Helm values on every pull request. A full run (the app, Fluent Bit and OpenSearch; one query's log line must arrive with `requestId`, `durationMs` and `schedulerWaitMs` as fields) runs on demand and whenever the kit's files change.
